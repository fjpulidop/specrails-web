# Specs and the shared backlog

A spec is the durable agreement for a change. It gives an implementation more than a chat request: an outcome, boundaries and evidence you can review.

## Make the contract useful

Describe the problem, expected behavior, acceptance criteria, constraints and affected repositories. Include concrete examples and failure cases. State what is outside scope so the agent can distinguish necessary work from adjacent ideas.

“Premium” describes the depth of the contract and authoring experience, not a guarantee that a model will implement it correctly. Review generated assumptions and make every important criterion observable.

## Keep one backlog

Missions and Board use the same project backlog. A multi-repository spec stays one spec with an explicit repository selection; it is not copied into unrelated backlogs. A spec without that selection uses the primary repository.

Add Spec opens in **Intent**, the default mode: describe the problem, not the solution, and Specrails writes the [intent](/docs/missions-intent-mode) and the spec derived from it for you to review. Then use [Quick](/docs/specs-add-spec-quick-mode) for a clear, focused request, [Explore](/docs/specs-add-spec-explore-mode) to work through uncertainty, or Raw to write the contract yourself. Review the draft before saving and launching it.
